# R2 ECU Studio: инструменты, VM и CAN

Дата: 25.10.2026. UI-05; проверка своего изменения по QA-07. Это отчёт о
реализованном клиенте и план следующих работ, а не подтверждение готовности ECU.
Запрошенные функции перенесены из требований пользователя и наблюдений за
интерфейсом. Скриншоты EMU PRO не доказывают внутренний алгоритм прошивки;
изображения, ресурсы и закрытый код производителя не копируются.

## Что уже работает

Клиент — существующее отдельное приложение Python/PyQt6. Новый проект получает
профиль `sport-gdi6`: 6 DI + 6 PI как опция, 2 ТНВД, 6 зажиганий, 1 DBW,
1 EWG, 1 lambda, 2 knock, 2 CAN, SENT/LIN. Это требуемые возможности проекта,
не автоматически обнаруженная плата. Формат v3 сохраняет явный профиль;
старые v1/v2 открываются как восьмицилиндровые legacy-проекты без потери карт.

Работают открытие/сохранение JSON, таблицы с двумя и тремя осями, выбор слоя,
undo/redo, поиск карт и защита несохранённых правок. Добавлены шесть
**искусственных** каналов с единицами и ограниченный график RPM. Симулятор
проверяет представление данных; он не исполняет алгоритмы двигателя или VM.

CAN definitions открывает DBC/CANX через настоящий парсер racing_dash:
выбор CAN1/CAN2/обе/из файла, просмотр сигналов, ID, единиц, масштаба и
предупреждений. Это предварительный просмотр: узлы проекта не создаются,
данные в ECU не записываются, CAN-кадры не отправляются.

## Инвентаризация требований

Статус «план» означает, что в этой ревизии нет работающего инструмента.
«Зависит от ECU» указывает необходимый контракт/испытание перед его реализацией;
пустые рабочие кнопки под видом готовых функций не добавлялись.

## Подтверждённые исходники racing_dash

Локальный источник: `C:/Projects/racing_dash`, репозиторий
[`rakyury/racing_dash`](https://github.com/rakyury/racing_dash), ревизия
`2c66c178083ae4bd0f2f0afe928ecd799af6347c`. Приватный репозиторий доступен
владельцу; ссылки сохраняют точную ревизию. Для vm.c, vm.h, expr_compiler.py,
bus_decode.py и can_import.py проверено совпадение локального Git blob с HEAD.

| Компонент | Исходник в racing_dash | Решение |
|---|---|---|
| VM | `shared/vm/vm.c`, `vm.h` | Общий C-код для PC и MCU; отдельный новый Python VM не нужен |
| Значения / состояние | `shared/channel_engine/channel.c`, `stateful_nodes.*` | Согласовать IDs, fixed-point, valid/stale и разрешения записи |
| Таймеры / фильтры / таблицы | `shared/timers`, `shared/filters`, `shared/tables` | Повторно использовать соответствующие узлы и порядок исполнения |
| Компилятор формул | `configurator_qt/src/core/expr_compiler.py` | Python компилирует выражение в bytecode общего C VM |
| Desktop binding | `configurator_qt/lvgl_lib/engine_host.c` | Выделить узкую C ABI без зависимости ECU-клиента от LVGL |
| Qt orchestration | `configurator_qt/src/core/live_engine.py` | Адаптировать lifecycle; не копировать зависимости dash-документа целиком |
| DBC/CANX import | `configurator_qt/src/core/can_import.py` | Уже включён как атрибутированный vendor-модуль и offline preview |
| Декодер CAN | `firmware/CM4/src/dash_can_decode.c`, `firmware/Shared/include/dash_can_decode.h` | Один native decoder для PC и целевой MCU, общий набор кадров |
| PC decoder binding | `configurator_qt/src/core/can_decode_c.py`, `lvgl_lib/can_decode_shim.c` | Проверить ABI/разрядность и повторно использовать |
| Обвязка сигналов | `configurator_qt/src/core/bus_decode.py` | Нативный decoder с Python fallback; перенести контракты полей и timeout |
| Transport | `configurator_qt/src/core/can_link.py`, `can_bulk.py` | Переносить framing/CRC/reassembly после согласования ECU endpoint |
| Adapter backend | `configurator_qt/src/core/can_eusb2can.py` | Отдельно проверить платформу/драйвер; бинарный vendor DLL не копировался |
| Экспорт / presets | `configurator_qt/src/core/can_export.py`, `can_presets.py` | Сохранять совместимость объектов, не создавать параллельный формат |

Для парсера опубликован отдельный
[provenance с точными изменениями](../configurator/power8gdi_configurator/vendor/racing_dash/PROVENANCE.md).
Исправлены зависание на большом масштабе, нулевая шкала, потеря флага extended
и коллизия multiplexor для одинаковых числовых standard/extended ID.
Дробный offset и непредставимый scale больше не округляются молча.
CANX остаётся совместимым с терпимым парсером racing_dash; предупреждение об
этом обязательно видно в preview. Полную проверку ECU-конфигурации он не заменяет.

## Где исполняется VM

В racing_dash реальный исполнитель — C VM: int32, RPN-байткод, стек 128,
буфер bytecode 32768 байт, до 64 программ. Python — компилятор и управление
сессией. `engine_host.c` вызывает тот же shared engine из PC DLL; логика узлов
таймеров, фильтров и таблиц находится также вне vm.c. Desktop live-loop использует
Qt timer около 30 Гц; это не подходящая по умолчанию частота ECU control-loop.

Нельзя судить о возможностях только по именам opcode: в этой ревизии
`OP_TABLE_2D/3D`, `OP_TIMER_VAL` и `OP_FILTER_VAL` в vm.c возвращают ноль;
рабочий путь узлов надо брать из общего pipeline. Перед ECU-адаптацией нужны
проверка поддерживаемых opcode/длины/стека, циклов зависимостей, бюджета времени,
диапазона каналов, качества входов и разрешённых выходов. Значение без valid/stale
не является достаточным основанием для управления мотором.

VM не получает прямого доступа к DI, зажиганию или моторным мостам. Приоритеты
защит и окончательное разрешение выходов остаются в проверяемом ядре ECU.
Интеграция native VM в прошивку ведётся отдельным firmware workstream;
этот клиентский commit не заявляет, что VM уже подключён к GUI или ECU.

## Порядок следующих итераций

1. Общая схема параметров/каналов/объектов с ID, единицами, revision и capability
   handshake; отдельные namespaces входов, вычислений и разрешённых команд.
2. Импорт CAN-объектов с diff и undo, общий native decoder, файловый replay;
   тесты CAN1/CAN2, standard/extended, Intel/Motorola, mux, timeout/validity.
3. Подключение native VM через отдельную библиотеку и штатный компилятор;
   соответствие PC/MCU по одному corpus, ограничения ресурсов и диагностика.
4. Project Tree, Variables Inspector, группы/таймеры/формулы, сохранение UI;
   затем логи, Logged Channels, частичный импорт и merge.
5. Device sessions/transport и чтение реальной телеметрии после согласованного
   протокола; отдельно работа с параметрами, permanent save и сервисные команды.
6. Калибровочные помощники и output tests после аппаратных/стендовых проверок.

Используем собственный клиент и собственную типизированную схему. TunerStudio
и INI не становятся обязательным форматом продукта. Консоль rusEFI — источник
проверенных подходов к соединению, диагностике и логам; переноса её Java-кода
в этой итерации нет. UI-наблюдения EMU PRO определяют удобство инструментов,
но не подменяют исходники racing_dash или проверку прошивки.
